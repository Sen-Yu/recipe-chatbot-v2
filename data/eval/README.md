# 역할별 평가 데이터셋

레시피 챗봇 v2의 베이스 모델 벤치마크(로드맵 1번)에 쓰는 평가 데이터입니다. 현재 버전 v0에는 5개 역할에 걸쳐 97개 케이스가 있습니다. 아직 동결 전이며, 동결은 로드맵 1.4에서 합니다.

## 요약

- 에이전트 역할마다 모델이 만들어야 하는 출력이 달라서 역할별로 파일을 나눴습니다.
- v0(2026-11-24)은 v1 테스트 문서에서 옮긴 케이스와 형식 확인용 수작업 케이스로 이루어져 있습니다.
- 선택 역할(21개)은 같은 날 추가했습니다.
- 동결한 평가 세트는 어댑터 학습 데이터(로드맵 4.1)에 절대 넣지 않습니다.

## 케이스 읽는 법

모든 케이스에 공통으로 들어가는 필드입니다.

| 필드 | 뜻 |
|---|---|
| `id` | 역할 접두어 + 번호 |
| `source` | 출처 |
| `tags` | 태그 |
| `note` | 메모 |

역할마다 입력과 정답(`expected`) 필드가 다릅니다.

| 역할 | 입력 | 정답 (`expected`) |
|---|---|---|
| 수퍼바이저 | `utterance`, `state`(보유 재료, 레시피 제목, 영양 정보 여부, 검증 미달 사유, 조건) | `next_any_of`: 정답으로 인정하는 다음 행동 목록. `constraints`: 발화에서 읽어야 하는 조건 (없으면 검사 안 함) |
| 재료 | `utterance`, `pantry`(현재 보유 재료) | `final_pantry`: 변경을 반영한 뒤의 보유 재료. `amounts`: 양까지 확인할 재료 (선택) |
| 레시피 | `utterance`, `pantry`, `constraints`, `dish_name`(이름 요청일 때), `previous_recipe_title`(재요청·변형일 때) | `must_not_contain`, `min_pantry_used`, `title_contains`, `dish_exists`, `max_cook_time` |
| 영양 | `recipe`, `nutrition`(코드가 계산한 값), `constraints` | `must_mention`(설명에 하나라도 들어갈 말), `substitutes_required` |
| 선택 | `options`(직전에 보여준 후보 제목), `utterance` | `gate`(결정 모델로 보내야 하는지), `final`(하나 확정·여러 개·되묻기·수퍼바이저), `number`, `rules_only`(규칙만으로 정해져야 하는지) |

## 정답을 정한 방법

**재료는 결과로 채점합니다.** 모델 출력(`IngredientUpdate`)을 코드(`apply_pantry_update`)에 반영한 뒤의 보유 재료를 정답과 비교합니다. 같은 결과를 내는 표현(예: 첫 턴의 `diff`와 `replace`)을 모두 정답으로 인정하기 위해서입니다.

**재료명은 대표명으로 씁니다.** 정답의 재료명은 동의어 사전의 대표명입니다 (예: 쇠고기 → 소고기, 달걀 → 계란). 채점할 때도 같은 사전으로 정규화합니다.

**수퍼바이저 정답은 여러 개일 수 있습니다.** 사람이 봐도 두 행동이 모두 맞으면 둘 다 `next_any_of`에 넣었습니다. 예: "매콤한 돼지고기 요리 추천해줘" → 레시피 또는 재료.

**레시피는 정답 문장이 아니라 조건으로 채점합니다.** 레시피는 정답이 하나가 아닙니다. 그래서 알레르기 재료 제외, 보유 재료 사용 개수, 제목, 조리 시간 같은 조건만 정답에 둡니다. 맛과 자연스러움은 1.5에서 정할 LLM 심사로 봅니다.

**요리 실존 여부는 v1 두 모델의 판정이 같을 때만 정답으로 씁니다.** 근거는 v1 웹검색 실존판정 20케이스입니다. claude-opus-4-8과 gemini-3.5-flash의 판정이 같으면 그 값을 정답으로 썼습니다. 판정이 다른 1개(`rec-014`, 무지개파스타)는 `dish_exists: null`(미확정)로 두었습니다. 이 케이스는 1.3 데이터셋 검증에서 사람이 정합니다.

## v1 케이스를 v2 정답으로 바꾼 규칙

v1은 분류기가 경로를 고르는 고정 그래프였습니다. v2는 수퍼바이저가 다음 행동을 고릅니다. 그래서 v1의 "예상 동작"을 v2의 다음 행동으로 바꿨습니다.

| v1 동작 | v2 정답 |
|---|---|
| 재료 추출(`initial`, `add`, `remove`, `replace`) | 수퍼바이저 `ingredient`, 재료 에이전트는 바뀐 뒤의 보유 재료 |
| 요리 이름 검색 | 수퍼바이저 `recipe`, 레시피 에이전트는 `dish_name`과 `title_contains` |
| "다른 거 없어?" 재요청 | 수퍼바이저 `recipe` (v1에서 '선택'으로 오분류됐던 케이스) |
| 관련 없는 질문, 미개발 기능, 정보 부족 | 수퍼바이저 `ask_user` (v2에는 별도 거절 경로가 없음) |
| 번호 목록에서 고르기 | 입력 게이트 → 결정 모델. 선택 데이터셋으로 평가 (초안 E1, 설계 기록 4장) |

## 부족한 부분과 채울 계획

v0은 형식과 채점 기준을 정하기 위한 출발점입니다. 벤치마크에 쓰기에는 수가 적습니다. 영양 역할은 v1에 케이스가 없습니다.

| 역할 | v0 | 목표 | 채울 방법 |
|---|---|---|---|
| 수퍼바이저 | 25 | 100 | 합성: 턴 중간 상태(재료 반영 후, 영양 계산 후, 검증 미달 후), 조건 추출, 변형 요청을 고르게 |
| 재료 | 18 | 100 | 합성: 양·단위 표현, 동의어, 비식재료 섞기, 구어체 |
| 레시피 | 29 | 60 | 합성: 알레르기·칼로리 조건 조합, 재료 1~2개, 변형 요청 |
| 영양 | 4 | 40 | 합성: 조건 초과·부족·충족, 계산 제외 재료 유무 |
| **합계** | **76** | **300** | |

| 항목 | 내용 |
|---|---|
| 합성 데이터 | 합성에는 생성 모델이 필요합니다. 클라우드 모델을 교사 모델로 쓸지는 아직 정하지 않았습니다 (설계 기록 7장). 정해지면 진행합니다. |
| 사람 검토 | 합성한 케이스는 1.3 데이터셋 검증에서 사람이 정답을 확인한 뒤에만 평가 세트에 넣습니다. |
| v1 대화 로그 | 실제 사용자 발화라 가장 좋은 출처입니다. 다만 S3에 있어 지금은 접근할 수 없습니다. 1.2 익명화를 거친 뒤에 씁니다. |
